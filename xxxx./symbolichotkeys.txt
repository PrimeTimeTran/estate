# Keybinding Pipelines

Estate's keybinding system provides a **single, declarative control layer** over macOS keyboard shortcuts.

The goal is to avoid multiple utilities independently intercepting keyboard events or modifying system behavior.

Estate should instead:

1. Read the existing macOS shortcut configuration.
2. Convert Apple's plist representation into editable JSON.
3. Normalize Apple's numeric/internal representation into a human-readable `schema.json`.
4. Let the user edit `schema.json`.
5. Validate the requested changes.
6. Generate Apple's plist representation from the schema.
7. Preserve a backup before applying changes.
8. Apply the resulting plist to macOS.
9. Provide a deterministic restore path.
10. Eventually support `diff`, `validate`, `apply`, and `restore` as Estate commands.

---

## Architecture

```text
                    ┌─────────────────────┐
                    │      schema.json     │
                    │                     │
                    │ Estate source of    │
                    │ truth / user config │
                    └──────────┬──────────┘
                               │
                               │ compile / translate
                               ▼
                    ┌─────────────────────┐
                    │ Apple shortcut JSON │
                    │                     │
                    │ numeric IDs         │
                    │ keycodes            │
                    │ modifier bitmasks   │
                    └──────────┬──────────┘
                               │
                               │ plutil
                               ▼
                    ┌─────────────────────┐
                    │       .plist        │
                    │                     │
                    │ macOS representation│
                    └──────────┬──────────┘
                               │
                               │ apply
                               ▼
                    ┌─────────────────────┐
                    │       macOS         │
                    │ System Preferences  │
                    │ / Keyboard Shortcuts│
                    └─────────────────────┘
```

The Apple plist format is an **implementation format**.

`schema.json` is the **human-readable Estate format**.

Do not make the numeric macOS IDs the primary Estate API.

---

## Pipelines

### 1. Apple source → plist JSON

Export the current macOS configuration into JSON for inspection and normalization.

```sh
plutil -convert json \
  -o ~/Desktop/symbolichotkeys.json \
  ~/Library/Preferences/com.apple.symbolichotkeys.plist
```

This produces:

```text
com.apple.symbolichotkeys.plist
        ↓
symbolichotkeys.json
```

The resulting JSON is a faithful representation of Apple's data.

It is **not yet Estate's schema**.

---

### 2. Apple plist → Estate schema

Estate should eventually transform Apple's representation into:

```text
schema.json
```

The schema should expose concepts such as:

```json
{
  "shortcuts": {
    "mission_control": {
      "name": "Mission Control",
      "platform": "macos",
      "enabled": true,
      "key": {
        "keycode": 126,
        "modifiers": ["control"]
      },
      "macos": {
        "symbolic_hotkey_id": 32
      }
    }
  }
}
```

The important distinction is:

```text
Estate ID:
    mission_control

        ↓

macOS ID:
    32
```

Estate should own this mapping.

This keeps the rest of the system independent from Apple's numeric identifiers.

---

### 3. Edit `schema.json`

The user edits only the Estate representation:

```text
schema.json
```

For example:

```json
{
  "shortcuts": {
    "estate.command_palette": {
      "name": "Estate Command Palette",
      "enabled": true,
      "key": {
        "keycode": 49,
        "modifiers": ["command", "shift"]
      }
    }
  }
}
```

The user should not normally edit:

```text
symbolichotkeys.json
```

or:

```text
com.apple.symbolichotkeys.plist
```

directly.

---

### 4. Validate before applying

Estate should validate the schema before touching macOS.

Eventually:

```sh
estate hotkey validate schema.json
```

Validation should detect things such as:

* unknown shortcut IDs
* invalid keycodes
* invalid modifiers
* duplicate bindings
* malformed platform configuration
* unsupported macOS shortcuts
* conflicting Estate bindings

No system files should be modified by validation.

---

### 5. Schema → Apple shortcut JSON

Estate compiles:

```text
schema.json
        ↓
Apple shortcut JSON
```

For example:

```text
estate shortcut ID
        ↓
macOS symbolic hotkey ID
        ↓
keycode
        ↓
modifier bitmask
        ↓
Apple JSON representation
```

This is where Apple's implementation-specific representation belongs.

---

### 6. Apple JSON → plist

Once validated and compiled:

```sh
plutil -convert binary1 \
  -o ~/Library/Preferences/com.apple.symbolichotkeys.plist \
  ~/Desktop/symbolichotkeys.json
```

This converts the JSON representation back into Apple's binary plist format.

**For the eventual Estate implementation, this should happen only after backup + validation.**

---

## Lifecycle / Utility Control

### 7. Backup before modification

Before applying any change:

```sh
cp ~/Library/Preferences/com.apple.symbolichotkeys.plist \
   ~/Library/Preferences/com.apple.symbolichotkeys.plist.backup
```

Preferably Estate should create **versioned backups** rather than continually overwriting one:

```text
backups/
    symbolichotkeys/
        2026-09-26T18-30-00.plist
        2026-09-26T19-12-14.plist
        2026-09-27T09-04-51.plist
```

That gives Estate an actual configuration history.

---

### 8. Diff before applying

Eventually:

```sh
estate hotkey diff
```

should show:

```text
Mission Control
  old: Control + Up
  new: Command + Shift + M

Estate Command Palette
  old: disabled
  new: Command + Shift + Space
```

No changes should occur during `diff`.

---

### 9. Apply

Only after validation and backup:

```sh
estate hotkey apply
```

Conceptually:

```text
schema.json
    ↓
validate
    ↓
backup current plist
    ↓
compile Apple representation
    ↓
write plist
    ↓
refresh macOS preferences
```

---

### 10. Restore

Estate should always have a deterministic escape hatch:

```sh
estate hotkey restore
```

or:

```sh
estate hotkey restore <backup>
```

Restoration should replace the current Apple configuration with a known-good previous version.

---

## Desired Estate CLI

Eventually the workflow should look like:

```sh
estate hotkey export
estate hotkey schema
estate hotkey validate
estate hotkey diff
estate hotkey backup
estate hotkey apply
estate hotkey restore
```

The normal development workflow becomes:

```text

└──────┬───────┘
```

## Design Principle

**Estate should manage configuration, not compete with macOS for raw keyboard events.**

Where macOS already provides a native shortcut mechanism, Estate should prefer configuring that mechanism over installing another event interceptor.

The Estate layer should therefore be:

```text
declarative
        +
validated
        +
versioned
        +
diffable
        +
reversible
        +
platform-aware
```

rather than:

```text
20 utilities
    ↓
20 event hooks
    ↓
20 competing configurations
    ↓
unknown keyboard state
```

The long-term goal is a **global interaction layer controlled from one Estate configuration**, while preserving macOS as the underlying authority for shortcuts that macOS itself can provide.

One thing I'd change from your original three-command list: **don't describe JSON → plist as "user-config → Apple OS/system."** There should be an Estate compile/validate/backup stage between those two. That's the part that makes this a proper configuration system rather than a dangerous plist editor.
