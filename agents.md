# AGENTS.md — Estate

## 1. Project Purpose

Estate is a local-first development platform that provides context, workspace boundaries, event capture, and AI-assisted software development workflows.

The SDLC module is responsible for orchestrating structured software development through explicit stages, persistent artifacts, agent execution, evaluation, and verification. It should behave as a controlled workflow rather than an unconstrained autonomous coding loop.

The system should remain modular and usable independently of any particular editor, UI framework, or model provider.

- **Separate orchestration from execution.** The SDLC pipeline determines what should happen next; the agent runtime handles model interaction and tool execution.
- **Make state explicit.** Stages, attempts, outcomes, and transitions should be represented through structured state rather than inferred from log messages.
- **Use persistent artifacts.** Intent, specification, plan, execution results, and verification evidence should be inspectable after a run.
- **Prefer bounded, evidence-driven execution.** Agents should follow an approved plan, inspect relevant context, make focused changes, and verify the results.
- **Treat failures as information.** Distinguish model failures, malformed outputs, filesystem errors, execution failures, failed evaluations, and exhausted retry policies.
- **Make retries purposeful.** A retry should address the previous failure or request a targeted revision. Do not repeat an identical failing operation indefinitely.
- **Keep infrastructure replaceable.** Model providers, tool adapters, MCP servers, UI clients, and host integrations should not define the core SDLC abstractions.
- **Avoid hidden environmental dependencies.** Prefer workspace-relative paths, explicit configuration, and injected runtime dependencies over hardcoded machine-specific paths.
- **Keep startup and cancellation responsive.** Background work should have clear ownership, cancellation behavior, and lifecycle management.
- **Make behavior observable.** Important transitions, decisions, executions, and failures should be recorded in structured events and logs.

## 3. SDLC Module

Location: `src/modules/sdlc/mod.rs`

The SDLC module coordinates a staged development lifecycle:

1. **Intent** — understand and formalize the user's goal.
2. **Spec** — define requirements, constraints, and expected behavior.
3. **Plan** — produce an actionable implementation and verification plan.
4. **Build** — execute the plan through the agent runtime.
5. **QA** — evaluate the implementation and its verification evidence.
6. **Complete** — record successful completion when the required acceptance criteria are met.

Human intervention must remain possible when the goal is ambiguous, the system cannot recover safely, or a decision requires authorization.

### Stage artifacts

The workflow uses Markdown artifacts and structured runtime state. Relevant artifact names include:

- `intent.md`
- `spec.md`
- `plan.md`
- `tests.md`
- `progress.md`
- `build.md`
- `verification.md`
- `sdlc.current.json`

The exact ownership and lifecycle of each artifact should be defined by the SDLC implementation. Do not assume that every artifact is generated by every stage or that all artifacts are always present.

### Stage responsibilities

- Intent must preserve the user's actual goal without prematurely committing to an implementation.
- Spec must turn the goal into explicit, testable requirements.
- Plan must describe concrete actions and expected verification.
- Build must execute against the plan rather than inventing an unrelated workflow.
- QA must evaluate evidence against the requirements and acceptance criteria.
- Complete must reflect a verified terminal outcome, not merely the end of a model response.

Keep prompts, templates, transition logic, state management, and execution mechanics separate where practical.

Prompt and template assets currently reside under `src/modules/sdlc/input/`. Prefer embedded assets through `include_str!` for compile-time-known prompts and templates rather than reading hardcoded source paths at runtime.

## 4. State, Evaluation, and Recovery

The pipeline must distinguish at least:

- Successful stage completion.
- Recoverable failure requiring revision.
- Execution or infrastructure failure.
- Failed acceptance criteria or verification.
- Human intervention required.
- Terminal failure or exhausted retry budget.

Do not collapse all unsuccessful outcomes into a generic failure or allow failures to silently restart the pipeline.

Evaluation thresholds and retry limits are configuration or policy decisions. Inspect their current implementation before changing them. Earlier development has involved changing retry behavior, including excessive repeated Intent attempts; do not assume a retry limit is enforced merely because a default constant exists.

A revision should carry forward the relevant failure evidence and explain what needs to change. Repeated attempts should be bounded, observable, and justified.

## 5. Agent Runtime and Execution

The agent runtime should provide the common execution context used by SDLC and other agent workflows.

Relevant concepts include:

- `AgentRuntime`
- `AgentTask`
- `AgentRun`
- `Agent` and its working-directory context
- Execution records and command history
- Runtime events and event delivery
- Workspace and task context
- Model generation and tool execution

Preserve the distinction between:

1. Constructing context and prompts.
2. Requesting model output.
3. Parsing and validating the requested action.
4. Authorizing and executing that action.
5. Recording execution results.
6. Evaluating whether the task or stage is complete.

Use execution records as evidence of what actually happened. Do not treat a model's claim that a command succeeded, a file was modified, or tests passed as proof.

Prefer focused workspace inspection and exact file paths over broad exploratory commands. Keep command execution bounded and surface errors to the orchestration layer.

When changing runtime event types or the event bus, maintain consistent event ownership and payload types across producers, subscribers, and UI projections. Avoid introducing parallel event systems without a clear reason.

## 6. Model, Tools, and MCP Boundaries

The SDLC workflow should not be coupled directly to a specific local model or MCP server.

- Keep provider-specific request and response handling behind a model integration boundary.
- Treat model output as untrusted structured input: validate it before execution.
- Keep tool discovery separate from tool authorization and execution.
- Require explicit policies for filesystem access, shell commands, and other side effects.
- Keep MCP transport and protocol details outside stage-transition logic.
- Provide sufficient context to the model without indiscriminately dumping the entire workspace or execution history.
- Respect model context limits and preserve the most relevant instructions, artifacts, and failure evidence.

When adding a tool or integration, document its ownership, configuration, permissions, failure behavior, and effect on cancellation.

Do not assume that an available tool is authorized to perform every action.

## 7. Workspace, Filesystem, and Persistence

Use the active workspace and injected runtime context to resolve paths.

Avoid hardcoded absolute paths such as `/Users/future/kb/project/...` in production logic. Paths must work across development machines and supported platforms.

The project has used `log/` for SDLC artifacts and debugging during development. Application-support storage has also been used for runtime logs and state. These locations must not be treated as interchangeable without an explicit storage policy.

Before changing persistence behavior:

1. Identify the canonical workspace and session directories.
2. Identify which component owns each artifact.
3. Check whether a path is source-controlled, generated, or application state.
4. Ensure directory creation and file writes return meaningful errors.
5. Verify that paths are valid and bounded before filesystem operations.

Keep logs, temporary files, session artifacts, configuration, and source templates conceptually distinct even if they temporarily share a directory.

## 8. Observability and Debugging

Use structured events and logs to make the workflow traceable.

Record enough information to reconstruct:

- The active SDLC stage and attempt.
- The task or session associated with the work.
- The outcome and reason for a transition.
- Relevant model-generation failures.
- The commands or tools actually executed.
- Execution results and verification evidence.
- The artifact paths involved.

Avoid logging unnecessarily large prompts or entire histories. Truncate verbose prompt content in diagnostic output while preserving enough metadata to identify the task and failure.

Do not silently swallow filesystem, IPC, event-delivery, model, or execution errors. Preserve the original error context when translating failures into SDLC outcomes.

## 9. Development and Verification Rules

Before modifying the SDLC implementation:

1. Inspect the relevant module, callers, types, and tests.
2. Identify the responsible layer before changing behavior.
3. Trace the state transition from input through execution to persisted outcome.
4. Prefer the smallest change that fixes the identified problem.
5. Add or update tests for the behavior and relevant failure paths.
6. Build and run the narrowest relevant verification first.
7. Report what was actually verified and what remains unverified.

Do not report successful verification solely because code compiled or an agent returned a successful status.
